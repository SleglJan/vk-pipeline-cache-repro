# vk-pipeline-cache-repro

A small two-process probe of `VkPipelineCache` behaviour: does cache data written by one process serve compute pipeline
creations in another process, and under which conditions? Written for AnyPS5 issue
[#11106](https://github.com/boykopovar/AnyPS5/issues/11106) (NVIDIA, Linux), so that the same steps can be repeated on
other GPUs, drivers and operating systems. Everything here is synthetic: the compute shaders are generated by a script,
no application or game data is involved, and the program treats the cache payload as opaque (it only records sizes and
`VK_EXT_pipeline_creation_feedback` results).

## Files

| file | purpose |
|---|---|
| `cacheprobe.cpp` | the probe (one C++20 file, Vulkan 1.1 instance; `VK_EXT_pipeline_creation_feedback` when present; `VK_EXT_subgroup_size_control` with `--subgroup32`/`--full`; `VK_EXT_descriptor_indexing` plus `VK_KHR_maintenance3` with `--uab`); every Vulkan name it uses is present in Vulkan-Headers 1.2.158 and later (names checked, not compiled against) |
| `gen_slow.py` | writes a GLSL compute shader whose body is N groups of three statements (plus one branch per 50) inside a loop bounded by specialization constant K0, so a creation takes the driver's compiler a measurable time; eight specialization constants select variants |
| `run_cases.sh` | the Linux driver for cases A-G below (bash, needs `glslc` and `python3`) |
| `cacheprobe-mesa.sh` | lets `run_cases.sh` drive `cacheprobe` on a Mesa driver (AMD RADV, Intel ANV): maps the two driver cache modes to Mesa's variables and picks the device (see Mesa drivers below) |
| `CMakeLists.txt` | `find_package(Vulkan)` build of `cacheprobe` |
| `LICENSE` | MIT |

## Build

Linux: a C++20 compiler, CMake 3.16+, the Vulkan loader and headers, `glslc` (shaderc, or the Vulkan SDK).

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

If your distribution does not ship the Vulkan headers, point CMake at a Vulkan-Headers checkout:
`-DVulkan_INCLUDE_DIR=/path/to/Vulkan-Headers/include`.

Windows: the Vulkan SDK (loader, headers, `glslc`), CMake, and MSVC or a GCC toolchain; the same two commands, except
that a Visual Studio generator ignores `CMAKE_BUILD_TYPE` and needs `cmake --build build --config Release` (see the
Windows note under Cases). The program uses nothing outside the C++ standard library and the Vulkan loader. We have not
built or run it on Windows.

## What the program does

```
cacheprobe [options] export <spv> <out-i> <out-ii>
cacheprobe [options] load <spv> <cache-file|none> [warm.spv]
cacheprobe [options] fill <spv> <count> <out.bin>
cacheprobe [options] probe <spv> <cache.bin> <seed>
```

- `export`: creates the pipeline in a fresh `VkPipelineCache` and writes that cache's data to `out-i`; creates it again in
  a new empty cache and writes that data to `out-ii`; a third creation with no cache shows the process's own state.
- `load`: optionally creates an unrelated pipeline first (`warm.spv`), then imports `cache-file` into a new cache and
  creates the pipeline from it (`none` = no cache, the cold reference).
- `fill`: creates `count` specialization variants (seeds 0 .. count-1, in that order) into one cache and saves its data.
- `probe`: imports a cache and creates variant `seed` from it.

Options: `--spec N` (N specialization constants, default 1), `--seed N` (the variant for `export` and `load`; `probe`
takes its variant from its last argument and `fill` compiles seeds 0 .. count-1, both ignore `--seed`), `--subgroup32`,
`--full` (`REQUIRE_FULL_SUBGROUPS`; implies `--subgroup32`), `--uab` (update-after-bind storage buffer layout), `--push`,
`--sets2`, `--pre FILE` / `--post FILE` (import another cache file before / after the one under test, into a separate
`VkPipelineCache` that is neither merged into nor passed to the creation), `--busy N` (N threads compile cold variants
of the shader under test while the creation runs), `--prefill N` (compile N cold variants into a scratch cache first;
with `load` and a `warm.spv` the variants are `warm.spv`'s), `--device N` (physical device index; the default is the
first NVIDIA device), `--any-vendor`. `--pre`, `--post` and `--busy` apply only to `load`; `--prefill` only to `load` and
`probe`; the other modes ignore them. `probe` prints its device line before it reads the variant argument, so that line
shows the `--seed` value (0 unless given); the variant is in the creation line.

Every creation under test prints one line (`fill` prints only variants 0, 1 and the last; `--busy` and `--prefill`
creations print no per-creation line, each mode prints one summary line), for example F3 here:

```
creation with the loaded cache: wall 26 ms, feedback valid cache-hit, driver 26 ms (stage cache-hit, 23 ms)
```

`cache-hit` is `VK_PIPELINE_CREATION_FEEDBACK_APPLICATION_PIPELINE_CACHE_HIT_BIT`; `wall` is the time around
`vkCreateComputePipelines`. A creation counts as served when it reports `cache-hit` and takes a small fraction of the
`load ... none` control. Each run also prints the device, driver version and `pipelineCacheUUID`; writer and reader must
agree on the UUID. `export` and `fill` print the size of the cache data they write; `load` prints the imported cache's
data size after the creation.

## Driver cache modes

The results depend on the driver's own shader disk cache. On Linux (NVIDIA):

- OFF: `__GL_SHADER_DISK_CACHE=0`.
- ON-EMPTY: the variable unset and `__GL_SHADER_DISK_CACHE_PATH=<fresh empty directory>`, so the process starts with
  an empty driver cache and the user's own cache is never touched.

`run_cases.sh` sets these per invocation; with a Mesa driver, `cacheprobe-mesa.sh` maps the two modes to Mesa's
variables (next section). On Windows we do not know a per-process equivalent; the tester chooses how to handle the
driver cache and should state it with the results. We ran no case against a populated driver cache, so results
obtained that way have no counterpart here and should be labelled as such.

## Mesa drivers (AMD, Intel)

`run_cases.sh` sets NVIDIA's cache variables for every step, and `cacheprobe` picks the first NVIDIA device by default.
`cacheprobe-mesa.sh` makes the same script run on a Mesa driver (RADV for AMD, ANV for Intel; we tried RADV only):
`run_cases.sh` runs the wrapper in place of the binary (`CACHEPROBE=./cacheprobe-mesa.sh`), and for each step the
wrapper maps the mode to Mesa's variables, picks the device and runs `build/cacheprobe`:

| `run_cases.sh` mode | NVIDIA variable the script sets | what the wrapper sets for Mesa |
|---|---|---|
| OFF | `__GL_SHADER_DISK_CACHE=0` | `MESA_SHADER_CACHE_DISABLE=true` |
| ON-EMPTY | `__GL_SHADER_DISK_CACHE_PATH=<fresh directory>` | `MESA_SHADER_CACHE_DIR=<the same directory>`; Mesa writes its caches inside it (here `mesa_shader_cache/` and RADV's `radv_builtin_shaders/`), and `run_cases.sh` empties it before each ON-EMPTY step |

Through the wrapper, no step reads or writes the user's own Mesa caches (`mesa_shader_cache`, RADV's
`radv_builtin_shaders`, under `$XDG_CACHE_HOME` or `~/.cache`). The wrapper maps only these two variables; a direct call
through it with neither set runs with the caller's own Mesa settings.

Device: `CACHEPROBE_DEVICE=N` makes the wrapper pass `--device N`; without it the wrapper passes `--any-vendor`, which
takes the first device the Vulkan loader lists, and that can be another vendor's GPU, an integrated GPU or a software
device (llvmpipe). On the RX 7900 XT machine below the loader listed the discrete GPU at 0, the Ryzen iGPU at 1 and
llvmpipe at 2; on ours the RTX 3080 at 0 and the Ryzen iGPU at 1. Every `cacheprobe` process prints the devices it sees
as `physical device N: <name> (vendor 0x....)` into `out/<timestamp>/cases.log` (the filtered summary shows only the
chosen `device ...` line), so run a short set first, read the indices, then the full run:

```
CACHEPROBE=./cacheprobe-mesa.sh ./run_cases.sh 300 10 2000 5                # tiny shaders, under a minute
grep -h 'physical device' out/<timestamp>/cases.log | sort -u               # <timestamp>: from the summary's 'full log:' line
CACHEPROBE_DEVICE=0 CACHEPROBE=./cacheprobe-mesa.sh ./run_cases.sh          # the full run on device 0
```

The summary's `device ...` lines must name the intended GPU and say `feedback ext`; in the short set some B7/B8 probes
miss by design (seeds a 10-variant cache does not hold). On our machine the short set on the Ryzen 9 7950X3D iGPU
(RADV, Mesa 26.2.4, `CACHEPROBE_DEVICE=1` next to the RTX 3080) took 12 s. AMDVLK, amdgpu-pro and other non-Mesa
drivers have their own cache controls, so the mapping does not apply to them; state the driver with the results.

## Shaders

```
python3 gen_slow.py 3000  slow.comp     # the working shader (875,328 B of SPIR-V after -O, about 219 K words)
python3 gen_slow.py 40000 huge.comp     # the large shader (10,787,548 B, about 2.7 M words)
glslc -fshader-stage=compute -O slow.comp -o slow.spv
glslc -fshader-stage=compute -O huge.comp -o huge.spv
glslc -fshader-stage=compute -O small.comp -o small.spv   # small.comp: the five lines below
```

`small.comp` (the unrelated warm-up pipeline) is written inline by `run_cases.sh`; its full text:

```
#version 450
layout(local_size_x = 64) in;
layout(constant_id = 0) const uint K = 1u;
layout(set = 0, binding = 0) buffer Out { uint data[]; } o;
void main() { o.data[gl_GlobalInvocationID.x] = gl_GlobalInvocationID.x * K; }
```

## Cases and exact invocations

`run_cases.sh [statements=3000] [fill=200] [huge=40000] [prefill=150]` runs all of them and prints a filtered summary;
the full log is `out/<timestamp>/cases.log`. `$OFF` and `$ON` stand for the two modes above; every line is a fresh process.

On Windows, run the same lines by hand: generate the three shaders with the commands above, then run each case line
with `build\cacheprobe.exe` (a Visual Studio generator ignores `CMAKE_BUILD_TYPE`; build with `--config Release` and
the binary is `build\Release\cacheprobe.exe`), leave out the `$OFF` / `$ON` prefixes, keep every `fresh` step's meaning
in mind (B8, C, D3, E, F2/F4/F6, G3/G4 ran with an empty driver cache here), and state with the results how the driver
cache was handled.

**A. One pipeline, OFF.** Export in process 1, load in fresh processes, for six option sets (`""`, `--subgroup32`,
`--full`, `--uab --push --sets2`, `--spec 8`, `--full --uab --push --sets2 --spec 8`):

```
$OFF cacheprobe load slow.spv none                                  # A0 control
$OFF cacheprobe <opts> export slow.spv i.bin ii.bin                 # A1
$OFF cacheprobe <opts> load slow.spv ii.bin                         # A2 (ii): empty cache's data after the repeat
$OFF cacheprobe <opts> load slow.spv i.bin                          # A3 (i): fresh cache's data after the compile
$OFF cacheprobe <opts> load slow.spv i.bin small.spv                # A4 (i) after an unrelated pipeline
```

**B. A 200-variant cache written OFF, and a single-pipeline file next to it.**

```
$OFF cacheprobe --spec 8 fill slow.spv 200 big.bin                  # B1 variants 0..199 in order, one cache
$OFF cacheprobe --spec 8 --seed 999 export slow.spv i999.bin ii999.bin   # B2 a variant not in big.bin
$OFF cacheprobe --spec 8 --seed 999 load slow.spv none              # B3 control
$OFF cacheprobe --spec 8 --seed 999 load slow.spv ii999.bin         # B4
$OFF cacheprobe --spec 8 --seed 999 --pre big.bin load slow.spv ii999.bin    # B5 big cache imported first
$OFF cacheprobe --spec 8 --seed 999 --post big.bin load slow.spv ii999.bin   # B6 big cache imported after
$OFF cacheprobe --spec 8 probe slow.spv big.bin <seed>              # B7 seeds 0 1 50 100 150 199
$ON  cacheprobe --spec 8 probe slow.spv big.bin <seed>              # B8 seeds 0 20 50 80 100 130 150 180 199, fresh empty driver cache each
```

**C. ON-EMPTY on the reading side** (fresh empty driver cache before each line):

```
$ON cacheprobe --spec 8 --seed 999 load slow.spv none               # C1 control
$ON cacheprobe --spec 8 --seed 999 load slow.spv ii999.bin          # C2
$ON cacheprobe --spec 8 --seed 999 load slow.spv i999.bin           # C3
$ON cacheprobe --spec 8 --seed 999 --pre big.bin load slow.spv ii999.bin     # C4
```

**D. Eight threads compiling cold variants during the creation.**

```
$OFF cacheprobe --spec 8 --seed 999 --busy 8 load slow.spv ii999.bin                 # D1
$OFF cacheprobe --spec 8 --seed 999 --busy 8 --pre big.bin load slow.spv ii999.bin   # D2
$ON  cacheprobe --spec 8 --seed 999 --busy 8 --pre big.bin load slow.spv ii999.bin   # D3
```

**E. ON-EMPTY on the writing side too.**

```
$ON cacheprobe --spec 8 --seed 777 export slow.spv i777.bin ii777.bin      # E1
$ON cacheprobe --spec 8 --seed 777 load slow.spv ii777.bin                 # E2
$ON cacheprobe --spec 8 --seed 777 load slow.spv i777.bin                  # E3
$ON cacheprobe --spec 8 --seed 777 --busy 8 --pre big.bin load slow.spv ii777.bin   # E4
```

**F. The large pipeline (huge.spv).**

```
$OFF cacheprobe --spec 8 --seed 555 load huge.spv none                        # F0 control
$OFF cacheprobe --spec 8 --seed 555 export huge.spv hoff_i.bin hoff_ii.bin    # F1
$ON  cacheprobe --spec 8 --seed 556 export huge.spv hon_i.bin hon_ii.bin      # F2
$OFF cacheprobe --spec 8 --seed 555 load huge.spv hoff_ii.bin                 # F3
$ON  cacheprobe --spec 8 --seed 556 load huge.spv hon_ii.bin                  # F4
$OFF cacheprobe --spec 8 --seed 555 --pre big.bin load huge.spv hoff_ii.bin   # F5
$ON  cacheprobe --spec 8 --seed 556 --pre big.bin load huge.spv hon_ii.bin    # F6
$OFF cacheprobe --spec 8 --seed 555 --post big.bin load huge.spv hoff_ii.bin  # F7
$OFF cacheprobe --spec 8 --seed 555 --pre big.bin load huge.spv hoff_i.bin    # F8
```

**G. A process that compiled 150 variants first** (`--prefill` compiles them into a scratch cache before the import).

```
$OFF cacheprobe --spec 8 --seed 555 --prefill 150 load huge.spv hoff_ii.bin slow.spv   # G1
$OFF cacheprobe --spec 8 --prefill 150 probe slow.spv big.bin 0                        # G2
$ON  cacheprobe --spec 8 --seed 556 --prefill 150 load huge.spv hon_ii.bin slow.spv    # G3
$ON  cacheprobe --spec 8 --prefill 150 probe slow.spv big.bin 0                        # G4
```

## Our results (RTX 3080, NVIDIA 615.78.08, Linux, an X display reachable with `DISPLAY=:0`)

Measured on 2026-10-26 with `run_cases.sh` at its defaults (one run, 13 minutes; the log is not included). Toolchain:
GCC 16.2.1, CMake 4.4.4, Vulkan-Headers 1.4.335 (`VK_HEADER_VERSION 335`), glslc from shaderc 2026.4 with SPIRV-Tools
1.4.363. Measured with an earlier revision of `cacheprobe.cpp` and `run_cases.sh` whose only differences are output lines
(the prefill line also searched the cache data for a string; the summary filter left out the `fill variant` lines); no number below
depends on them. Linux note: give writer and reader the same `DISPLAY`; here every process could reach the X display and
all 70 reported the same `pipelineCacheUUID`. Cold references: `slow.spv` 816-853 ms (A0, B3, C1), `huge.spv` 20.4 s (F0).
Single-pipeline cache data is 241-246 KB for `slow.spv` and 2,739,533-2,739,534 B for `huge.spv`; B1 compiled its 200
variants in 164 s into 25,170,750 B.

Reproduced the pattern of the issue only in part:

- **B8**: an ON-EMPTY reader of the 25 MB, 200-variant cache written OFF: of the nine probed variants, 0, 20, 50 and
  80 were served (12-14 ms, `cache-hit`) and 100, 130, 150, 180 and 199 missed (810-829 ms, `cache-miss`). This is the
  shape the issue reports for the application's cache file, at a much smaller size.

Did not reproduce it:

- **A**: single-pipeline cache data served in every fresh process, for all six option sets, for both (i) and (ii) and
  after an unrelated pipeline: 2 ms against 853 ms cold.
- **B4-B6, C, D, E**: a single-pipeline file served next to the 25 MB cache imported before or after it (2 ms), with
  the driver cache ON-EMPTY on the reading side (C: 8-12 ms) or on both sides (E: 8 ms; 13 ms with eight threads
  compiling), and with eight threads compiling meanwhile (D: 2 ms OFF, 13 ms ON-EMPTY).
- **B7**: an OFF reader was served all six probed variants of the 200-variant cache (0 to 199), 2 ms each.
- **F**: the large pipeline's 2.7 MB data served, OFF, alone and with the 25 MB cache imported before or after it
  (26-27 ms), and, ON-EMPTY, alone and with the 25 MB cache imported before it (114-118 ms), against 20.4 s cold.
- **G**: a process that had compiled 150 variants first (121-122 s, 24.5-24.8 MB of cache data) still imported the
  large pipeline's file (23 ms OFF, 71 ms ON-EMPTY) and the 200-variant cache's variant 0 (2 ms OFF, 5 ms ON-EMPTY).

Nothing synthetic reached the scale of the issue (a 147 MB cache; per-pipeline files of 3.5-6.6 MB that did not serve):
the largest single-pipeline file here is 2.7 MB and the largest cache 25 MB, and every single-pipeline file served.

## Other results

**RX 7900 XT, RADV, Mesa 25.2.8 (Ubuntu 24.04 container), Linux 7.3**, run by [@ondra2305](https://github.com/ondra2305)
on 2026-10-26: `run_cases.sh` at its defaults through `cacheprobe-mesa.sh` with `CACHEPROBE_DEVICE=0`, 6.6 minutes, valid
feedback on every creation. On RADV a served creation reports `cache-hit` in the pipeline feedback and `cache-miss` in
the stage feedback (every served creation of this run, and of our short set on the iGPU).

- Cold references (A0, B3, C1): `slow.spv` 198-202 ms. Every import of single-pipeline data was served at 0 ms with
  `cache-hit`: A2-A4 for all six option sets, B4-B6, C2-C4, D1-D3 and E2-E4.
- The 200-variant cache was 37,720,000 B. B7 and B8 served every probed variant at 0 ms with `cache-hit`, B8 (the
  reader with an empty Mesa cache) included; on the NVIDIA run above B8 missed five of its nine variants.
- `huge.spv`: 28.9-29.9 s cold; F3-F8 served at 1-2 ms.
- G: the 150-variant prefill took 28.7-30.2 s; the imports after it were served at 1-2 ms.
